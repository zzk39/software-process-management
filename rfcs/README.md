# RFC 目录说明

## 什么是 RFC？

**RFC**（Request For Comments，"征求意见稿"）最早由互联网工程任务组（IETF）在 1969 年使用，用于在工程师之间公开、有序地讨论设计方案。如今它已成为软件工程常见的 **设计文档形式**：

> 在写代码之前，先把要做什么、为什么做、怎么做、不做什么写清楚，让团队成员评审达成共识。

一句话：**RFC = 团队做决策前的书面提案**。

## 为什么要写 RFC？

在这个项目里，我们是 6 个人协作开发。如果没有统一的设计文档，很容易出现：

- A 以为预约可以跨天、B 以为不行，到集成才发现矛盾
- 接口字段各自随便起名，前后端对不上
- 改了一个参数，不知道影响哪些人
- 交接、复盘、考核时翻聊天记录已经找不到"当初为什么这么做"

RFC 解决的问题：

| 问题 | RFC 的作用 |
|---|---|
| **避免方向错误** | 写下来才能被评审，动手前就能发现问题 |
| **降低协作成本** | 接口契约固化，前后端/上下游并行开发 |
| **留下决策痕迹** | 每个"为什么"都有出处，审计/复盘有据可查 |
| **便于上手** | 新成员或 reviewer 读 RFC 就能理解模块全貌 |

## 本项目的 RFC 约定

### 1. 一一对应：RFC 严格映射 story.md 章节

story.md 分 21 章（一到二十一），每章是一个 Feature。**每个 Feature 对应一份 RFC**。这样做：

- 用户故事不会漏：每条 `A4.1` 都能在对应 RFC 里找到
- 不跨界设计：每份 RFC 只对一个 Feature 负责，边界清晰
- 便于分工：一份 RFC 就是一个人的"设计任务"

| RFC 编号 | Story 章节 | Feature |
|---|---|---|
| RFC-001 | 一 | A1 身份识别 |
| RFC-002 | 二 | A2 浏览自习室 |
| ... | ... | ... |
| RFC-021 | 二十一 | 非功能需求 |

完整映射见 [`RFC-000-index.md`](RFC-000-index.md)。

### 2. 统一模板

每份 RFC 必须包含以下 8 小节：

1. **背景与目标** — 为什么做，解决谁的什么问题
2. **用户故事** — 逐条对应 story.md，保持编号一致（如 A4.1, A4.2...）
3. **数据模型** — 新增/修改哪些表/字段
4. **API 设计** — HTTP 方法、路径、入参、出参、错误码
5. **前端交互** — 页面、组件、关键交互流程
6. **验收标准（AC）** — 可执行、可测试的要点
7. **非目标** — 这份 RFC 不做什么（避免 scope creep）
8. **依赖与风险** — 依赖哪些其它 RFC、有什么技术风险

### 3. 状态流转

```
Draft  →  Accepted  →  Implemented  →  Closed
  │         │             │               │
  写完      评审通过       写完代码         功能上线
```

- **Draft**：正在写，可以被修改
- **Accepted**：组长/小组 review 通过，进入开发
- **Implemented**：代码已合入主干，但还没发版
- **Closed**：已经上线且稳定运行，一般不再修改

状态写在 RFC 开头的元信息里：

```markdown
- **迭代**：1
- **状态**：Draft
```

## RFC 与其它文档的关系

```
story.md               ── 需求（"用户想要什么"）
    │
    ├─► rfcs/RFC-XXX   ── 设计（"我们打算怎么做"）
    │       │
    │       ├─► backend/app/api/xxx.py   ── 实现
    │       └─► frontend/.../xxx.vue
    │
    └─► docs/ITERATION_1.md  ── 任务看板（"这一迭代谁做什么"）
```

- `story.md` 是**需求源头**，由产品/老师给出
- `rfcs/` 是**设计结论**，由开发者对需求做技术分解
- 代码是 RFC 的**落地**
- `docs/ITERATION_1.md` 是**项目管理视角**，把 RFC 切成任务分给具体的人

## 怎么写一份新 RFC？

1. **复制模板**：挑一份已有的 RFC（如 `RFC-004-create-reservation.md`）作为起点
2. **改元信息**：编号、章节、负责人、迭代
3. **逐条对齐 story.md**：不要丢故事，也不要瞎加故事
4. **写数据模型 + API**：前后端据此并行开工
5. **列验收标准**：每条都能写成一个 pytest 用例或手工验证步骤
6. **提 PR 评审**：文件命名 `RFC-XXX-kebab-case.md`，在 PR 中 @组长 review
7. **被 accept 后**：状态改 `Accepted`，开始写代码

## 什么时候需要新写一份 RFC？

- story.md 新增一个章节 → 必须新 RFC
- 现有 RFC 的范围已经太大，拆出子模块 → 可以新开 RFC，用 `RFC-XXX-sub` 命名
- 现有 RFC 的结论要大改（比如 API 结构重构）→ 直接修改原 RFC，但在文件末尾加"变更记录"表

## 什么时候**不**需要 RFC？

- 修 bug（直接提 PR + issue 描述）
- 改错别字、UI 调色、依赖升级等低风险改动
- 临时调试代码

## 一个好的 RFC 长什么样？

- ✅ **每条用户故事都能在 AC 里被验证到** —— 这是 RFC 和需求的对齐度
- ✅ **API 的入参/出参/错误码都写出来** —— 前后端不需要口头沟通就能对接
- ✅ **有"非目标"** —— 明确告诉别人哪些想法这次不做，避免后期 scope creep
- ✅ **有依赖** —— 读者能判断这个 RFC 是不是被 blocked
- ❌ 只罗列故事但不给数据模型 —— 实现者仍然要从零想
- ❌ 把实现细节（变量名、SQL 语法）都写出来 —— RFC 写意图，不写代码
